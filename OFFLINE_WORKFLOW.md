# AttendTrack — Офлайн режим

> Как приложението работи без интернет връзка.

---

## Архитектура накратко

```
┌─────────────────────────────────────────────┐
│              Устройство (таблет)             │
│                                             │
│  ┌──────────┐    ┌──────────┐    ┌───────┐  │
│  │ Next.js  │───▶│IndexedDB │◀───│  SW   │  │
│  │  (PWA)   │    │ (Dexie)  │    │(кеш)  │  │
│  └──────────┘    └──────────┘    └───────┘  │
│        │                                    │
│        │  (само при онлайн)                 │
└────────┼────────────────────────────────────┘
         │
    ╔════╧════╗
    ║  Spring ║
    ║  Boot   ║
    ╚═════════╝
```

| Слой | Технология | Роля |
|------|-----------|------|
| PWA Shell | `@ducanh2912/next-pwa` + Workbox | Зарежда приложението без интернет |
| ML модели | Service Worker `CacheFirst` (30 дни) | ONNX + MediaPipe WASM от кеша |
| Данни | IndexedDB чрез Dexie.js | Работници, обекти, чакащи записи |
| Синхронизация | `SyncBanner` + event listeners | Автоматично при връщане на интернет |

---

## Фаза 1 — Първоначална настройка (изисква интернет)

Трябва да се извърши **веднъж** докато устройството е онлайн.

```
Таблет онлайн
     │
     ▼
Влизане в /verify
     │
     ├─▶ GET /api/sites  →  списък с назначени обекти
     │
     ├─▶ GET /api/sync/site/{id}  (за всеки обект паралелно)
     │        │
     │        ├── данни на обекта (координати, checkpoints, работно време)
     │        └── работници + face descriptors (~4 KB на работник)
     │
     ├─▶ Записва всичко в IndexedDB
     │        ├── db.siteInfo   → обекти
     │        └── db.workers    → работници с лицеви дескриптори
     │
     └─▶ Service Worker кешира:
              ├── Next.js app assets (HTML, JS, CSS)
              ├── ONNX модел (MobileFaceNet ~2 MB)
              └── MediaPipe WASM (~15 MB)
```

**След тази фаза устройството може да работи напълно офлайн.**

## Фаза 2 — Стартиране офлайн

При следващо отваряне на приложението **без интернет**:

```
Таблет офлайн
     │
     ▼
Браузърът зарежда PWA shell от Service Worker кеша
     │
     ▼
/verify се отваря → syncAll() се опитва да достигне сървъра
     │
     ├── navigator.onLine === false  →  пропуска API заявките
     │
     └── Зарежда директно от IndexedDB
              ├── db.siteInfo  →  sitesMap (обекти)
              └── db.workers   →  работници + дескриптори

     ▼
Камерата стартира → ML модели от Service Worker кеша
     │
     ▼
Приложението е напълно функционално ✓
```

> **Изключение:** Ако устройството **никога** не е имало интернет, IndexedDB е празна и приложението показва грешка. Необходима е поне **една** успешна онлайн сесия.

## Фаза 3 — Сканиране офлайн

```
Работник застава пред камерата
     │
     ▼
MediaPipe FaceLandmarker → 478 landmark точки
     │
     ▼
MobileFaceNet ONNX → 512-dim ArcFace embedding
     │
     ▼
Cosine similarity 1:N срещу db.workers (от IndexedDB)
     │
     ├── Съвпадение намерено
     │        │
     │        ▼
     │   resolveWorkerSite()
     │        ├── Проверява всички обекти на работника
     │        ├── GPS координати → isWithinAnyCheckpoint()
     │        └── Връща { siteId, locationValid }
     │
     │        ▼
     │   handleRecord() — записва в db.pending:
     │        ├── workerId, siteId, type (CHECK_IN / CHECK_OUT)
     │        ├── lat, lng, locationValid
     │        ├── faceConfidence
     │        ├── recordedAt (локално време)
     │        └── status: 'pending'
     │
     └── Няма съвпадение → ManualOverrideModal (ако е нужно)
```

**Записът е локален и моментален — не зависи от интернет.**

## Фаза 4 — Синхронизация при връщане на интернет

`SyncBanner` следи за интернет и trigger-ва синхронизация автоматично:

```
Интернет се възстановява
     │
     ├── window 'online' event  ──────────────────┐
     ├── document 'visibilitychange' (таб на фокус)│
     └── 30 s fallback interval (само брой записи) │
                                                   │
                                    ───────────────▼
                                          syncNow()
                                               │
                                    ┌──────────▼──────────┐
                                    │ db.pending           │
                                    │ status = 'pending'   │
                                    │ → маркира 'syncing'  │
                                    └──────────┬──────────┘
                                               │
                                    Групира по siteId
                                               │
                              ┌────────────────┴────────────────┐
                              │                                 │
                    POST /api/attendance/sync           POST /api/attendance/sync
                    (Обект А)                           (Обект Б)
                              │                                 │
                         Успех ✓                          Грешка ✗
                         bulkDelete                       reset → 'pending'
                              │                           (retry при следващ trigger)
                              └────────────────┬────────────────┘
                                               │
                                    refreshCount() → UI update
```

### Какво се показва на потребителя

| Ситуация | Banner |
|----------|--------|
| Офлайн, без чакащи записи | `📵 Офлайн` |
| Офлайн, с чакащи записи | `📵 Офлайн · 5 чакащи записа` |
| Онлайн, синхронизира | `↻ Синхронизиране...` (spin) |
| Онлайн, всичко синхронизирано | *(banner скрит)* |

---

## Защита срещу двойно изпращане

```
syncNow() извикана два пъти едновременно
     │
     ├── Проверка: syncingRef.current === true  →  втория call се отхвърля
     │
     └── Записите са маркирани 'syncing' преди изпращане
              │
              └── Ако syncNow() стартира отново преди края:
                       WHERE status = 'pending'  →  връща 0 записа  →  exit
```

---

## Частична грешка (един обект недостъпен)

```
5 записа: 3 за Обект А, 2 за Обект Б
     │
     ├── POST Обект А  →  ✓  →  изтрити
     └── POST Обект Б  →  ✗  →  reset 'pending'
                                      │
                                      └── Retry при следващ 'online' event
                                          или visibilitychange
```

---

## Граничен случай — работник в два обекта

При лицево разпознаване `resolveWorkerSite()`:

```
Работник Иван → назначен в Обект А и Обект Б
     │
     ├── GPS в радиуса на Обект А  →  siteId = А, locationValid = true
     ├── GPS в радиуса на Обект Б  →  siteId = Б, locationValid = true
     └── GPS извън всички обекти   →  siteId = А (първи), locationValid = false
                                        (запис се прави, флаг е false, нотификация към admin)
```

## Ограничения

| Ограничение | Причина |
|-------------|---------|
| Изисква поне 1 онлайн сесия преди офлайн работа | IndexedDB трябва да е попълнена |
| При смяна на работници/обекти — нужен е ръчен resync | Бутонът `↻` в горния ъгъл на /verify |
| Face descriptors не се обновяват офлайн | Нужен е `GET /api/sync/site/{id}` |
| Background Sync (при затворен браузър) — не е имплементиран | Записите се качват при следващо отваряне |

---

## Препоръки за deployment

1. **Зареди приложението онлайн поне веднъж** на всяко устройство преди употреба на терен.
2. **Пускай ръчен resync** (`↻`) сутринта или след промяна на работници.
3. **Не затваряй браузъра** докато има чакащи записи (жълтия/синия banner).
4. Устройството трябва да е **инсталирано като PWA** (Add to Home Screen) за пълно кеширане на ML моделите.
